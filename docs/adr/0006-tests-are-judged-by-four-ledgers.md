# Tests are judged by four ledgers that leave nothing unexplained, with mutants as the measure

Decided by the maintainer on 2026-11-17, in the eight decisions of the test review's spec ([#275](https://github.com/hirunefu/smock/issues/275)). The maintainer asked for a fundamental review of smock's tests that aims at 100% as mutation testing and similar measures judge it, removes the tests that are not needed, and adds the missing tests of boundary values and main use cases. Here "100%" means that nothing is left unexplained in four ledgers: coverage, mutation, boundaries and use cases. No percentage is a target or a gate: scores are reported per package and never gated, because a number that gates invites tests written to move it, and because coverage was high where the tests were weak. At d953f320 the in-process tests covered 96.0% of the instrumentation points outside `server` and `cmd/smock`, yet of 250 mutants sampled from the pure packages, 243 compiled and only 77.4% of those were killed, and 37 of the 39 survivors read by hand sat on covered lines; `grpc` and `usage` had survivors at 100% point coverage. Point coverage has no implicit else, no condition outcomes and no loop back-edges, so it cannot see such gaps. So coverage is necessary, and the mutants are the measure: a survivor is resolved by a test that kills it, by a code change where the survivor proves code redundant, or by a reviewed entry in one checked-in exclusion list. Packages climb a ladder: L1 coverage, L2 no pseudo-tested function, L3 nothing unexplained on the lines a branch changes, and L4 nothing unexplained over the pinned set. All 19 pure packages go to L4, ten first, then nine (decision 1), and so does the package without I/O that later receives `server`'s pure parsers, `serverparsers`, by the maintainer's decision of 2026-11-17. Every expected value a test adds comes from a named source, never from the code's current output, and a test goes only when a mechanical rule proves that nothing is lost. [How tests are judged](../../CONTRIBUTING.md#how-tests-are-judged) in CONTRIBUTING holds the terms and the rules that contributors follow; this ADR records what was decided and why.

## Operator set v1

The operators that make the mutants are pinned as a version, v1: BODY, ROR, IFC, LCR, NOT, DEL, BOOL, AOR, INT and STR, defined in [Operator set v1](../../CONTRIBUTING.md#operator-set-v1). A change to them, the rule that picks an alternative included, needs the maintainer's approval and shows in the weekly report, so that the meaning of "zero" cannot drift. STR is in the set because a mock server's behaviour is mostly strings: header names, content types, JSON keys, status texts and log lines. Sites come from a parser, not from a lexer, and each report gives, per package, the sites each rule skipped beside the survivors, so that a "zero" always says what it is zero of.

The pinned set holds one mutant per position, two for INT where it is an operand of a comparison or an index, and a fixed rule chooses the alternative, so that a runner cannot pick the alternatives that are easiest to kill. One mutant per line, chosen by operator priority, was rejected: of the 24 survivors of the sample first read as real, it would have picked another site for 16. Every site was rejected as what L4 counts: stage 1 alone would then hold about 1,200 to 1,700 survivors instead of about 760 to 1,090 (estimates), and the maintainer reads every exclusion in the protocol packages and in `serverparsers`, and one in five of the others. The full set, every alternative that an operator of v1 defines at every position, is still run, monthly and before each release, and reported.

### The four choices the spec left open

The spec left four choices of v1 open: which alternative IFC and STR take at a position, which replacement INT takes outside comparisons and indexes, and whether ROR also swaps `==` and `!=`. The maintainer settled them on 2026-11-17:

- **IFC takes the alternative under which the code that the condition guards never runs**: false for the condition of an `if` or an `else if`, of a loop, and for a match arm's guard; true for the condition of a `guard` statement, whose `else` then never runs. The guarded code is where a refusal, a limit or a special case lives, and a mutant that skips it is killed only by a test that needs it: one with an input on the far side of the check. That is the input the sample's survivors lacked most: of the 39 read by hand, 19 lacked a boundary or negative input. The other alternative runs the guarded code for every input, so wherever that code is a refusal, the main use case kills it: a request refused whatever it holds fails every test that expects an answer. On a loop it would also make the loop never end, and a time-out is the costliest outcome. Forcing a `guard` statement's condition to false would be that same easy alternative, which is why the rule is stated by what never runs, not by a value. The other alternative is in the full set.
- **STR changes one character**: the first character of the literal's text, outside any interpolation, becomes `_`, or `-` when it already is `_`; an empty literal becomes `"_"`. STR is in v1 for the strings that clients and users see letter for letter, and the use-case ledger asks that every message a user can see be asserted at least once; at d953f320, 22 messages were asserted by no test. A one-character change keeps the text well-formed: `_` is allowed in a header name and in a JSON key, and it is no letter, so a comparison that ignores case, as header names are compared, cannot make the change equivalent. Only a test that checks the exact text kills it. An empty string can fail elsewhere, as an empty header name is not a valid one, so a test that never checks the text could still kill it. The empty string is in the full set.
- **INT takes n+1 outside comparisons and indexes**, or n-1 where n+1 does not fit the literal's type. INT gave 24 of the sample's 55 survivors, the most of any operator. An integer outside a comparison is a size, a count, a code, a mask, a step or a constant of a wire format, and the smallest change to it is killed only by a test that depends on its exact value, as the boundary ledger asks of a limit, and as the tests that pin gRPC's status codes do for values a spec fixes. 0 is a larger change, which many tests kill without depending on the value; in place of a loop's step, it makes a loop that never ends, and so a time-out, the costliest outcome: in the sample, time limits of 5 to 10 times the normal run let 8 of 250 mutants take 22% of the time. n-1 turns a step of 1 into that same 0. The cost of n+1 is that it is equivalent more often, on a sentinel or on an offset applied to both sides of a comparison; such mutants go through the three steps of an equivalence claim. INT's alternatives are n+1, n-1, and 0 where n is not 0: n-1 and 0 are in the full set.
- **ROR does not swap `==` and `!=`**, in either set. The swap inverts the comparison, so any test that reaches it and observes its result kills it: it would add a mutant at every equality to every run, and tell little about a missing input. Where the comparison is a whole condition, IFC already forces that condition. The gaps the sample found at comparisons, such as the far side of the range checks in `usage` and `metrics`, are what the boundary alternative reaches.

### The details the mutation runner settled

A parser needs more than the operators and the four choices to find the sites. The mutation runner's ticket ([#299](https://github.com/hirunefu/smock/issues/299)) settled the rest, and the maintainer approved it on 2026-11-17 as part of v1. [Operator set v1](../../CONTRIBUTING.md#operator-set-v1) in CONTRIBUTING states each detail in full:

- **BODY has one default value for each kind of return type**: `()`, `false`, `0` for every type of number, `'\u{0}'`, the empty string, byte string, array and map, `null` for `Json`, `Iter::empty()`, `None` for an option, `Ok` of the default for a `Result`, and a tuple of defaults. A function whose return type has none, such as a type parameter or a type of smock's own, has no BODY mutant: its site is skipped and counted, like the spec's other skipped sites, so that a zero of BODY says what it leaves out. A default for each type of smock's own would need the runner to know how to build each one. BODY replaces the body of a top-level function or method, trait implementations included, not of `init`, `main`, a local function or a closure, and a body that already is the default is no site.
- **IFC forces every condition that guards code**: that of an `if` and an `else if`, of a `while` loop and a `for` loop with a condition, a match arm's guard and a `guard` statement's condition. A condition that binds a name with `is` takes IFC's false as `false && (condition)`. A plain `false` would leave the name unbound where the guarded code uses it, so the mutant would not compile, and every such condition would lose its site: 544 positions of the pinned set in the pure packages at be2b8e0b. `false && (condition)` never evaluates the condition, so the guarded code never runs, as the first choice above asks, and the name stays bound. Forced to true, the name would still be unbound, so that alternative is skipped, and a `guard` statement that binds a name (277 of the 544) has no mutant in the pinned set.
- **DEL deletes calls and assignments that are statements**, compound assignments and those to a field or an element included: one whose value its block drops, or the last statement of a block whose value is `Unit`. Deleting them leaves code that still types. It does not delete the only statement of a function's body, whose BODY mutant is the same.
- **INT is in a comparison or an index** when it is an operand of `<`, `<=`, `>`, `>=`, `==` or `!=`, or the index of an element or a slice, directly or through `+`, `-`, `*`, `/` and `%`. A literal inside arithmetic there moves the boundary as a literal alone does: one of the sample's survivors in `usage` sat in `kib <= 0x7fffffffffffffffL / 1024L`. An alternative must fit the literal's type, so no mutant fails to compile for a literal out of its range.
- **STR changes string and byte-string literals**, interpolated ones and those over several lines included, but not character literals. An escape is one character, and a literal that writes no character outside its interpolations gets `_` at the start of its text, as the empty literal does. Its scope holds `serverparsers` beside `server`: the parsers that move out of `server` keep the scope they had there, so a move takes no site out of v1.
- **Literals in patterns are no sites**, since v1's operators change expressions and a pattern is none. Nor are ranges, whose `<` and `=` compare nothing, nor `not(...)` calls, which are not NOT's prefix `!`.
- **Two more rules skip a site**, beside the spec's three: IFC's true, and LCR at an `&&`, where an operand binds a name with `is`, since the name would then be unbound where it is used; and AOR at a `+` with a string literal as an operand, since strings have no `-`. Each report counts them, as it counts the others.
- **Where two sites make the same mutant, one is kept**, so that a mutant is built, run and counted once: the one in the pinned set, then the first of BODY, ROR, LCR, NOT, BOOL, AOR, INT, STR, IFC and DEL.

## What L4 and a release read

L4 is defined over the pinned set, and the weekly run executes exactly that set over the pure packages, so the weekly run verifies L4. A release reads the same set (decision 7): for the packages at L4, the latest weekly run over the pinned set must show no unexplained survivor before a release, on the tag's commit or on an ancestor whose later changes the changed-lines reports cover or touch no non-test source of a package at L4. The release checks it before it publishes, beside the check that CI passed on the tag's commit, so a release may wait for one run. The monthly run over the full set is report-only: its survivors at the other alternatives are listed apart, and they stop no merge and no release and do not count towards L4. So the ticket of each package going to L4 has the pinned set as its target. A survivor whose only covering exclusion has gone stale counts as unexplained in the weekly run, the release check and every count for L4; the check before a merge reports it without stopping the merge.

The checks run on pushes to every branch but `main` (decision 3), because smock merges branches locally and opens no pull requests, so a gate on pull requests would never run on its own work. The stop is in the merge procedure: report-only at first, and once a package reaches L4, an unexplained survivor on lines of that package that a branch changes stops the merge into `main`.

## Agreement with ADRs 0001 and 0005

- **ADR 0001 holds: no new C seam.** An uncovered point or a survivor that only an OpenSSL or file-system failure reaches is excluded in the category FAULT, which has nothing to do with a Stub's Fault. No C is written to inject such failures.
- **The decision that ADR 0005 asks for.** ADR 0005 says that a design that wants HTTP/2 code in a package without I/O needs a new decision, because the no-I/O check forbids it. This is that decision: smock's own HTTP/2 request checks, which use no moonhttp type, only smock's own request type, `http1`'s public checks and `definitions`' host normalisation, may live in the package without I/O that receives `server`'s pure parsers (decision 2). That package imports no moonhttp: when it is made, it joins the packages that `scripts/check-no-io.sh` lists, and that check fails a listed package that imports a module other than the protocol modules, MoonBit's core and the other listed packages. Anything that needs a moonhttp type, such as counting a field section against moonhttp's own bound, stays in `server`.
- **ADR 0005's overlaps are kept.** The e2e tests that check the HTTP/2 rules and limits moonhttp enforces, as well as smock's own, so that an upgrade that drops one fails them, are a keep reason under the removal rule: no removal batch takes them because another test covers the same points or kills the same mutants.

## Considered Options

- **A target or a gate on a percentage of coverage or of killed mutants.** Rejected: it invites tests written to move the number, and the sample showed survivors on covered lines in packages at 100% point coverage. Scores are reported per package, for reading, and never gated.
- **Line coverage as the coverage ledger.** Rejected: a line that is only partly covered counts as covered, so line figures overstate coverage. The ledger reads moon's point coverage from the bisect report, and line figures are shown only beside it.
- **A third-party mutation tool.** Rejected: the most complete one skips nested modules, which are 6 of the workspace's 7 modules. The runner lives in the repository.
- **The full set as what L4 and a release read.** Rejected (decision 7): a release would wait for the monthly run, and every alternative at every position would need triage before a package could reach L4. The full set is reported monthly instead, apart.
- **A gate on pull requests.** Rejected, as above: it would never run on this project's own work.
- **Removing tests by text similarity, or by a greedy cover of coverage.** Rejected: at a similarity of 0.85 or more, 1,449 pairs of tests share only the harness's shape, and a greedy cover by coverage keeps 15 of `grpc`'s 52 tests and drops its boundary tests. Nor would removal make CI faster: the 53 e2e tests measured as candidates save about 4 s together (estimate). A test goes only under the removal rule, with its proof.
- **A seam in C to inject OpenSSL or file-system failures.** Rejected by ADR 0001; such code is excluded as FAULT.
- **Bulk mutation runs on a developer's machine.** Rejected: they would tie a machine up for hours. Bulk runs go to Actions, sharded within the account's 20 concurrent jobs. Single mutants and the diff mode run locally, and so do two named exceptions: step 1's replay of the 250 sampled mutants and the held-out set, which stays on the maintainer's machine.

## Consequences

- **The rules for tests change for everyone.** The oracle rule, extending the existing test first, the snapshot audits, and the removal rule with its keep reasons apply to every change, as CONTRIBUTING writes them. `moon test -u` stays a convenience: what it fills is checked against a source before it is committed, and the runner never passes it.
- **The maintainer's time.** About 35 to 70 hours over the review (estimate), most of it reading exclusions while the pure packages climb to L4. Only the maintainer fills in an exclusion's reviewer, and an equivalence claim reaches the maintainer only after the comparison of the compiler's output and an adversarial agent (decision 4). Expected values pass a check of their own first: a separate agent context that wrote none of the tests checks against their sources every value that step 1 adds and the snapshots that each package's audit draws. The maintainer reads only what it finds in disagreement, and, in step 1, the sources it finds unclear.
- **CI's wall time stays about 5 minutes.** Every addition is a job beside the existing ones, never a step on the path of the arm64 native test job. The bulk runs are scheduled or started by hand, on Actions.
- **Small code changes outside the tests.** `server`'s pure parsers move into a new package without I/O, and `cmd/smock` writes its coverage counters at exit when an environment variable is set, inactive otherwise (decision 2). Dead code is deleted with the maintainer's approval, not excluded, as step 1 deletes the Mock's candidate lookup in `definitions` and two messages that no input reaches, in `yaml` and in `template`. None of these changes what smock does.
- **The measure is measured too.** The held-out set of mutants, never gated on and never shown to an agent that writes tests, shows whether the tests catch more bugs or merely fit the operators. A ratchet on each package's number of sites, a forced-fail self-test and a weekly canary keep the runner from reaching zero by being weakened.
- **The four ledgers' baselines**, measured at d953f320, are in [The four ledgers](../../CONTRIBUTING.md#the-four-ledgers). They are where the review starts, not targets.
